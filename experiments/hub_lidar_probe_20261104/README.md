# Hub LiDAR and controller decision observation

Seed 123, OL1, unmodified simulator, NullRHI, 6 m/s bounded VEL diagnostic with static candidate 1→3 route. The route controller used GPS+IMU diagnostic pose and LiDAR; ROS graph snapshot shows no debug pose subscriber. The observer passively recorded command trace, controller telemetry and 23 LiDAR point clouds near the hub. Sensors and commands are recorded for diagnosis; no GT was used for control or for these observations. `manifest.json`/logs have binary, settings, route and controller hashes; observer snapshot preserves source. The observer's source and the runner used here are included as `*_snapshot.py`.

At route station 685–695 m, 546 controller telemetry records reported 406 `COMMAND_BRAKING`, 121 `COMMAND_BLOCKED`, 18 `LIDAR_TRACK`, and one `LIDAR_HEIGHT_RECOVERY`. The latest saved scan shows many returns in an approximate forward cylinder centered toward the static spline 3 endpoint; in the height bands −4..−2, −2..0, 0..2 m relative NED z there were 372, 2683 and 1390 points, with minimum forward coordinate about 1.33 m. This is consistent with a blocked direct candidate, but does not identify the object, prove collision geometry, or establish a causal defect in the controller. Bands above this region have fewer or zero returns, which do not certify free space.

`hub_analysis.json` was produced by `scripts/analyze_hub_lidar.py`: it transforms sensor-frame points using the most recently received GPS/IMU sample and −0.05 m sensor offset, not an interpolated pose. Individual cloud/source timestamp differences are recorded. Point clouds are raw float XYZ in each compressed NPZ and include metadata; telemetry messages retain source data and callback wall/monotonic/ROS clocks. A GDB breakpoint pauses execution and adds timing effects. No stage 4/5/6 was reached.
